## Narration N0: spike, measure Kokoro-82M on this PC (2026-10-07)

Spec: [`specs/2026-10-07-kokoro-narration.md`](../specs/2026-10-07-kokoro-narration.md) ·

**Problem.** Before building the narration UI, we need to know whether Kokoro-82M can
speak fast enough on this CPU (the GPU is reserved for Whisper) and which model variant
and settings to use.

**Change.**

- `app/requirements.txt`: added `kokoro-onnx>=0.6.1,<0.7` (installs onnxruntime 1.30.0,
  espeakng-loader 0.2.4, phonemizer 3.4.0; numpy 2.5.3 stays as it is).

  (fp32, int8, voices) matches the release. The 7 language samples are in
  `models/kokoro/samples/` (gitignored).
- Docs: `performance.md` (new Kokoro section), ADR 0001 → **Accepted** (one check still
  open, see below), spec (fp32, 4 threads, 6-word first-chunk cap, `MAX_CHARS` 120,
  decision 4 resolved), test plan (first-chunk cases; es/fr added to T-TTS-2),
  `current-state.md` (narration setup steps, next task N1).

## Narration N1: split window, STT left and TTS right (2026-10-07)

Spec §3.1 and §8 (N1) of [`specs/2026-10-07-kokoro-narration.md`](../specs/2026-10-07-kokoro-narration.md).

**Problem.** Narration needs its own half of the window. Today's speech-to-text UI has to
move into a left pane without changing how it behaves.

**Change.**

- `app/app.py`:
  - New `_build_panes`: a horizontal `tk.PanedWindow`. The left pane (`STT_MIN_W` 700)
    holds the existing controls, transcript and status line, unchanged. The right pane
    (`TTS_MIN_W` 420) has a "Text to speech" header, a placeholder and its own status

**Problem found after the first version (user report: "application shuttering on the
screen", windows opening and closing by themselves).**

- The layout tests opened 3 **visible** Wisper windows on every `node tools/verify.mjs`
  run, and verify runs after every agent turn (Stop hook), on pre-commit, and in review.
  The agent's screenshot probes and the reviewer's test runs added more.
  **Fix:** the test window is transparent (`-alpha 0`) and has no taskbar button
  (`-toolwindow`). It stays mapped, so geometry can still be measured.
- With pytest's default fd capture, creating the Tk window failed to read `tk.tcl` in
  **6 of 20** runs, and the fixture's `pytest.skip` hid it. A plain script creating the
  window 10× (with or without transparency) never failed.
  **Fix:** `pyproject.toml` `addopts = "-q --capture=sys"` (**0 of 20** runs fail) and
  the skip is removed, so a Tk problem now fails loudly.

| layout tests × 20, `--capture=fd` | 6/20 runs with a skip |
| layout tests × 20, `--capture=sys` | 0/20 |
| layout tests × 20 with the project config (after the fix) | 0/20 skips, failures or errors |

**Review (code-reviewer agent).** No blocking findings in `app.py` or the docs. Three
test gaps, all fixed in `test_window_layout.py`:

| # | Finding | Fix |
|---|---|---|
| 1 (medium) | Teardown didn't wait for the worker; after monkeypatch was undone, a late worker could load the real GPU model | `win.worker.join(timeout=5)` + assert it stopped |

**Lesson → CLAUDE.md.** One rule added: tests that build a Tk window keep it invisible
and rely on `--capture=sys`; don't launch the real app from the agent without asking.
